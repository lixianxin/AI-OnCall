# 客户端开发 - 工作计划

负责人：<客户端负责人>

定位：基于现有 `compose_chat` Android Demo，改造并实现一个协议驱动的开放式 Tab 容器，承载服务端下发的业务 Tab，并提供 AI OnCall 助理入口、聊天展示和异常态处理。客户端重点证明“业务 Tab 可以通过统一协议动态接入容器”，并支撑和服务端、协议端、AI 方向的端到端联调。

## 一、核心产出

- 可运行的 Android Demo，支持登录、主框架、动态 Tab、示例业务 Tab 和 AI OnCall 入口。
- 客户端 Tab 容器实现，能够根据服务端下发的 `TabDefinition` 动态渲染底部导航、页面标题、TitleBar 和功能按钮。
- 客户端网络接入层，支持登录、用户信息、Tab 列表、会话创建、消息历史和 AI OnCall SSE 流式响应。
- 示例业务 Tab，用于验证协议字段、权限、生命周期、TitleBar 扩展和按钮扩展。
- AI OnCall 页面，支持用户输入、消息列表、流式文本展示、代码块展示、工具调用事件展示和失败重试。
- 异常态与受限态展示，包括未登录、登录失败、网络异常、权限不足、版本不兼容、Tab 加载失败和 AI 服务不可用。
- 客户端联调说明与运行说明，包括 Android Studio 启动方式、真机调试说明、服务端地址配置方式和常见问题。

## 二、客户端设计范围

### 2.1 App Shell 与基础运行

- 使用现有 Android 工程作为基础，优先保证原 Demo 可以在 Android Studio、模拟器或真机上运行。
- 梳理现有 `app`、`base`、`proxy` 模块职责，保留可复用的 Compose UI、ViewModel 和基础模型。
- 新增或整理客户端配置入口，用于切换 Mock Server、局域网服务端和最终演示服务端地址。
- 保留必要的原 IM Demo 能力作为参考，不将腾讯 IM SDK 作为本课题服务端能力的核心依赖。

### 2.2 登录与身份状态

- 对接服务端 `POST /auth/login`，获取 token、用户信息和权限列表。
- 对接 `GET /auth/me` 或等价接口，支持启动后恢复用户状态。
- 客户端本地保存短期 token 和用户基础信息。
- 根据登录态控制主界面、受限态和重新登录路径。
- 展示登录失败、token 失效、网络异常等状态。

### 2.3 动态 Tab 容器

- 对接服务端 `GET /tabs`，获取 `TabDefinition` 列表。
- 根据 `TabDefinition` 动态渲染主导航和业务入口，避免把业务 Tab 全部硬编码在本地。
- 支持至少两类 Tab：
  - 内置 Native 示例 Tab，例如工作台、协议示例页。
  - AI OnCall Tab 或固定入口。
- 根据协议字段处理 Tab 图标、标题、入口路由、权限、版本和扩展配置。
- 对权限不足、容器版本不满足、入口类型不支持等情况展示明确提示。

### 2.4 TitleBar 与功能按钮扩展

- 根据 `TabDefinition.titleBar` 渲染页面标题、返回按钮、右侧操作按钮。
- 支持常见按钮动作，例如刷新、帮助、打开 AI OnCall、复制配置、查看详情。
- 对未知 action 做兜底提示，避免客户端崩溃。
- 与协议端确认 TitleBar 字段默认值和兼容策略。

### 2.5 生命周期与容器事件

- 结合协议端定义的生命周期，客户端在 Tab 创建、展示、隐藏、销毁、配置变化时记录或触发对应事件。
- 第一版以客户端内部日志和示例 Tab 回调为主，证明生命周期可以被容器统一管理。
- 后续可扩展为业务 Tab 可感知的 Kotlin interface 或统一事件分发。

### 2.6 AI OnCall 页面

- 对接服务端会话接口，创建或恢复 AI OnCall 会话。
- 对接 AI OnCall SSE 接口，支持增量消息展示。
- 支持消息类型：
  - 用户文本消息。
  - AI 文本增量消息。
  - 代码块或配置示例。
  - 工具调用开始、结果、失败事件。
  - 错误和重试提示。
- 页面展示重点围绕协议问答、接入方案生成、示例配置生成和错误诊断。

### 2.7 异常态与演示链路

- 为最终演示准备可控状态：
  - 正常登录并展示 Tab。
  - 权限不足 Tab。
  - 版本不兼容 Tab。
  - AI 流式回复。
  - AI 服务失败或网络失败。
- 配合服务端 Mock 数据完成演示，不依赖生产级复杂数据。

## 六、技术选型说明

客户端技术栈沿用现有项目方向，选择 Kotlin + Jetpack Compose + MVVM。

- Kotlin：与现有工程一致，适合表达协议数据类、接口和异步逻辑。
- Jetpack Compose：现有项目已经使用 Compose，适合快速构建动态 UI、状态驱动页面和聊天流式展示。
- MVVM：现有代码已有 ViewModel 基础，学习和改造成本低；适合将 UI、状态和数据请求分层。
- StateFlow / Compose State：用于表达登录态、Tab 列表、加载状态、错误状态和 AI 消息流。
- OkHttp：项目已引入 OkHttp，可用于 REST 请求和 SSE 流式响应；后续如需要可补充 Retrofit/Moshi 或 kotlinx.serialization。
- 本地 Mock + Go Mock Server 双阶段：本地 Mock 用于客户端先行开发，Go Mock Server 用于前后端稳定联调。
- 真机优先展示：相比模拟器更接近实际演示环境，也更容易验证局域网服务端访问、网络异常和输入体验。

暂不优先引入复杂依赖注入、数据库缓存、完整多模块重构或生产级账号体系。第一版目标是稳定跑通协议驱动接入和 AI OnCall 主链路，复杂能力作为后续扩展。

## 七、客户端验收标准

- Android Demo 能在 Android Studio 中构建并运行，至少支持一台真机或模拟器展示。
- 登录成功后能够从服务端获取用户信息和权限。
- Tab 列表由服务端配置驱动，客户端不依赖固定写死的业务 Tab 列表。
- 至少一个示例业务 Tab 可以按协议展示标题、入口、TitleBar 和功能按钮。
- 权限不足、版本不兼容、网络失败等状态有明确 UI 提示。
- AI OnCall 页面能够展示 SSE 增量回复和工具事件。
- 客户端与 Go Mock Server、PostgreSQL 版本服务端至少各完成一次主链路联调。
- 文档中说明客户端运行方式、服务端地址配置方式、真机调试方式和已知限制。
