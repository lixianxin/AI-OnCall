# 服务端答辩演讲稿

各位老师好，我负责的是 OpenTab 项目的服务端部分。

这个服务端主要支撑两个核心能力：开放式 Tab 容器和 AI OnCall。客户端负责页面展示，服务端负责账号登录、Token 校验、Tab 下发、团队权限、审批日程等业务数据，以及 AI 会话和流式输出。

我这部分重点讲五个设计点。

第一是整体架构。

服务端使用 Go + Gin，并按 routes、middleware、services、policies、repositories、cache 分层。routes 负责接口入口，middleware 处理鉴权、审计和 request_id，services 编排业务流程，policies 集中处理权限判断，repositories 负责数据访问。

这里比较关键的是 Repository 层。它同时支持 Memory 和 PostgreSQL 两套实现。前期客户端还在开发时，可以用 Memory 数据先联调；后期切换到 PostgreSQL 后，接口格式保持稳定。这样能减少团队协作时的接口反复变动。

第二是登录鉴权。

用户登录成功后，服务端生成随机 token，并把 session 写入 auth_sessions 表。后续客户端请求都携带 Bearer Token。服务端会校验 token 是否存在、是否过期、是否已经 logout 吊销，然后组装 CurrentUser，里面包括 user_id、团队、角色和权限码。

为了减少每次请求重复查数据库，我加入了 Redis 缓存。Redis 缓存 token session 和用户上下文。权限或团队关系变化时，服务端会主动清掉对应缓存。Redis 只负责加速，最终状态仍然以 PostgreSQL 为准。

第三是权限控制。

我做的是资源级权限判断。用户访问同一个接口时，服务端还会判断用户能不能访问这条具体资源。比如启用一个 Tab，服务端会检查这个 Tab 是否是系统 Tab、是否本人创建、是否发布到全公司、是否发布到当前团队、是否发布给当前用户，以及用户是否拥有对应权限码。

团队成员管理也做了服务端兜底。当前设定一个用户最多只有一个启用团队，所以管理员把成员加入新团队时，服务端会先停用旧团队关系，再启用新团队关系，避免客户端漏操作造成数据不一致。

第四是查询性能优化。

项目里有很多列表接口，容易出现 N+1 查询。比如 AI 最近会话列表，如果查到 20 个会话后，再对每个会话单独 count 消息数，就会产生很多额外查询。我把这类逻辑改成批量查询和 GROUP BY 聚合。

同样的优化也用在团队成员统计、审批日程公告的团队名称补齐、管理员用户团队关系查询上。再结合 Redis 缓存鉴权上下文，可以降低高频接口对数据库的压力。

第五是 AI OnCall 流式输出优化。

客户端请求 AI 时，先进入我的服务端。服务端负责鉴权、创建会话、保存消息、调用 AI 服务、解析 SSE，再流式返回给客户端。

这部分我做了并发限制、取消生成、同一会话重复生成自动取消旧任务、心跳、双缓冲平滑输出和失败降级。双缓冲的思路是：AI 原始输出先进入服务端队列，再由平滑输出模块按稳定节奏推给客户端。这样 AI 输出忽快忽慢时，客户端看到的内容会更稳定。

总结来说，我的服务端重点解决的是开放式 Tab 和 AI OnCall 背后的后端问题：身份可信、权限可控、数据隔离、查询稳定、流式输出可用。服务端承担安全边界和状态一致性，客户端专注展示和交互。
