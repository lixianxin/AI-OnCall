# OpenTab 服务端核心设计

## 项目定位

OpenTab 服务端承担开放式 Tab 容器的后端控制能力，负责账号登录、权限校验、Tab 动态下发、业务数据隔离、AI OnCall 会话管理和流式输出稳定性。

服务端技术栈：

- Go + Gin：提供 HTTP API。
- PostgreSQL：保存用户、团队、Tab、业务数据和 AI 会话。
- Redis：缓存登录态和用户上下文，减少高频鉴权查询。
- SSE：支撑 AI OnCall 流式回答。

---

## 1. 整体架构

### 设计目标

服务端采用分层架构，把 HTTP 接入、业务编排、权限判断、数据访问和缓存能力拆开管理。这样可以让接口联调、数据库切换、权限扩展和性能优化都有明确的修改位置。

### 架构图

![整体架构](assets/答辩图/01-整体架构.png)

### 核心实现

- `routes` 负责请求参数解析和响应返回。
- `middleware` 统一处理 Bearer Token、request_id 和审计日志。
- `services` 负责登录、Tab、团队、审批、日程、AI 会话等业务流程。
- `policies` 集中管理权限判断规则。
- `repositories` 抽象数据访问，支持 Memory 和 PostgreSQL 两套实现。

### 设计价值

- 前期可用 Memory 数据支撑客户端联调。
- 后期切换 PostgreSQL 后，客户端接口保持稳定。
- 权限、缓存、数据库查询优化可以分别演进。
- 单元测试可以直接基于 Memory 仓库运行，验证成本更低。

## 2. 登录鉴权

### 设计目标

登录态需要具备完整生命周期：登录生成、请求校验、过期失效、退出吊销、缓存加速。

### 鉴权流程

![登录鉴权](assets/答辩图/02-登录鉴权.png)

### 数据设计

`auth_sessions` 保存登录会话：

- `token_hash`：保存 token 哈希，避免明文 token 直接入库。
- `user_id`：关联用户。
- `expires_at`：过期时间。
- `revoked_at`：退出登录后的吊销时间。
- `created_at` / `updated_at`：状态追踪。

### Redis 加速

高频接口都会经过鉴权，重复查询 session、用户权限和团队关系会增加数据库压力。服务端使用 Redis 缓存两类数据：

- token session：判断 token 是否有效。
- CurrentUser：缓存用户权限码、团队角色、团队 ID。

权限或团队关系变化后，服务端主动删除对应用户缓存，保证缓存不会长期保留旧权限。

### 设计价值

- token 支持过期和 logout 吊销。
- 服务端掌握登录态最终状态。
- Redis 减少重复数据库查询。
- Redis 异常时可回退 PostgreSQL，接口正确性不依赖缓存。

## 3. 权限控制

### 设计目标

权限判断覆盖接口访问和资源访问。用户调用同一个接口时，服务端还会继续判断用户是否能访问具体的 Tab、团队或业务数据。

### Tab 访问判断

![权限控制](assets/答辩图/03-权限控制.png)

### 权限来源

服务端综合以下信息判断权限：

- 用户身份：当前登录用户由 token 解析得到。
- 团队关系：用户所在团队、团队角色。
- 权限码：例如 Tab 管理、审批查看、日程查看等。
- Tab 发布范围：全公司、团队、指定用户。
- 资源归属：本人创建、团队数据、系统内置数据。

### 团队一致性

当前项目设定一个用户最多只有一个启用团队。管理员把成员加入新团队时，服务端会在事务中停用该用户旧团队关系，再启用新团队关系。

### 设计价值

- 防止客户端只隐藏入口导致的接口越权。
- Tab 发布范围可以灵活支持公司、团队、指定用户。
- 管理员操作不完整时，服务端仍能维护团队关系一致性。
- 后续扩展更细粒度角色时，可以继续沿用权限码和策略层。

## 4. 查询性能优化

### 设计目标

列表页和高频鉴权接口需要控制数据库查询次数，避免数据量增加后接口明显变慢。

### N+1 查询优化

AI 最近会话列表需要返回每个会话的消息数。逐条统计会产生 N+1 查询：

![查询性能优化](assets/答辩图/04-查询性能优化.png)

优化后使用批量聚合，查询次数基本保持稳定。

### 已优化场景

- AI 最近会话：批量统计每个会话的消息数。
- 团队列表：批量统计成员数和主管数。
- 审批列表：批量补齐团队名称。
- 日程列表：批量补齐团队名称。
- 公告列表：批量补齐团队名称。
- 管理员用户列表：批量查询用户团队关系。

### 高频鉴权优化

每个受保护接口都需要鉴权。服务端使用 Redis 缓存 token session 和 CurrentUser，把重复的用户上下文查询从数据库转移到缓存层。

### 设计价值

- 列表接口查询次数更稳定。
- 数据量增加时，接口不会因为逐条查询快速变慢。
- Redis 降低高频鉴权对 PostgreSQL 的压力。
- 性能优化不改变客户端接口格式。

## 5. AI OnCall 流式输出优化

### 设计目标

AI OnCall 需要处理流式响应中的真实问题：响应慢、输出忽快忽慢、重复生成、用户取消、AI 服务异常、SSE 长连接空闲。

### 流式链路

![AI OnCall 流式输出优化](assets/答辩图/05-AI流式输出.png)

### 双缓冲机制

AI 服务返回的原始内容会先进入服务端缓冲，再分阶段推送给客户端：

1. 原始输入队列：接收 AI 服务返回的 token、tool、done、error 等事件。
2. 平滑输出队列：按固定节奏和合适大小切片，再推送给客户端。

### 并发与取消

- 全局并发限制：控制同时运行的 AI 生成任务数量。
- 用户级并发限制：避免单个用户连续发起大量生成。
- 同会话重复生成处理：新生成开始时取消旧生成任务。
- 取消生成：客户端取消后，服务端取消上下文，停止读取和转发。

### 稳定性处理

- 心跳：长时间无内容时维持 SSE 连接。
- 失败降级：AI 服务异常时返回兼容的错误事件。
- 消息保存：用户消息和 AI 消息进入服务端会话模型，支持历史记录拉取。

### 设计价值

- 客户端看到的 AI 输出更平滑。
- 重复点击不会产生多个回答互相覆盖。
- 用户可以主动取消正在生成的内容。
- AI 服务异常时客户端能收到明确错误状态。
- AI 对话进入服务端会话体系，便于后续追踪和诊断。
